GET/about 200

I'm Seth. I build and run the integration layer between systems that each believe they are the source of truth: student information systems, ERPs, workflow engines, payment and messaging providers, and the custom apps people actually use every day.

Most of my career was at Idaho State University, where I went from a one-person web shop to leading the Ellucian Ethos integration initiative across the campus's enterprise systems. Since 2025 I've been at DualEnroll, engineering the workflows and integrations that move dual-enrollment students between high schools, colleges and their SIS platforms.

I care about contracts and failure modes more than frameworks. If an integration can't be replayed, observed and explained at 3 a.m., it isn't done.

  • Idempotent by defaultEvery write carries a key; every retry is safe. Duplicate records are a design bug, not an ops problem.
  • Observable end to endCorrelation ids from the first request to the last webhook, so root cause takes minutes instead of a war room.
  • Schema is the conversationField mappings, enums and edge cases written down and versioned before code is, so both sides agree on what "enrolled" means.

personal · 2026worldbuilding as code

Omniverse — a version-controlled multiverse

A shared tabletop setting kept as a git repository and Obsidian vault. Every place, person and faction is a note with a stable ID; everything that happens is an event with a schema: type, severity, where, participants, visibility, and deltas with explicit from/to values.

Campaigns fork the canon at a point in time and play inside their own instance. When a session matters, qualifying events are proposed upstream as a pull request — replayed against canon in world-date order, and rejected as a "reality rift" if a from value no longer matches. An AI dungeon master reads state from the files, logs seeded dice rolls, and never edits canon directly.
